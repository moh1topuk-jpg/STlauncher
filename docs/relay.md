# Реле для «сервера для друзей»

Игрок запускает сервер Minecraft у себя дома, а друзья должны как-то до него достучаться.
Проброс порта на роутере есть не у всех и работает не у всех (общий адрес у провайдера),
поэтому лаунчер умеет ходить через реле: и хозяин, и гость сами подключаются к реле, а
оно перекладывает байты между ними. Ни VPN, ни драйверов, ни прав администратора.

Реле — отдельная маленькая программа `stlauncher-relay` (исходники в
[`src/STlauncher.Relay`](../src/STlauncher.Relay)). Она живёт на VPS владельца, а не в
лаунчере. Без неё прямое подключение через UPnP работает как раньше, а способ «через реле» просто
отвечает «не настроено».

## Сборка

```powershell
.\scripts\publish-relay.ps1
```

Скрипт кладёт два готовых файла, которым не нужен установленный .NET:

- `artifacts/relay/linux-x64/stlauncher-relay` — около 13 МБ, для VPS;
- `artifacts/relay/win-x64/stlauncher-relay.exe` — около 12 МБ, чтобы попробовать у себя.

Папка `artifacts/` в git не попадает. Другая архитектура:
`.\scripts\publish-relay.ps1 -Runtimes linux-arm64`.

## Запуск на VPS (systemd)

1. Скопировать файл и сделать его исполняемым:

   ```bash
   scp artifacts/relay/linux-x64/stlauncher-relay root@ВАШ_СЕРВЕР:/usr/local/bin/
   ssh root@ВАШ_СЕРВЕР chmod 755 /usr/local/bin/stlauncher-relay
   ```

2. Создать `/etc/systemd/system/stlauncher-relay.service`:

   ```ini
   [Unit]
   Description=STlauncher relay
   After=network-online.target
   Wants=network-online.target

   [Service]
   ExecStart=/usr/local/bin/stlauncher-relay
   Restart=on-failure
   RestartSec=3

   # Реле ничего не читает и не пишет на диск, поэтому ему не нужен ни свой
   # пользователь, ни доступ к системе: systemd даёт временного и закрывает остальное.
   DynamicUser=yes
   NoNewPrivileges=yes
   ProtectSystem=strict
   ProtectHome=yes
   PrivateTmp=yes
   PrivateDevices=yes
   LimitNOFILE=8192

   # Настройки, если нужны не те, что по умолчанию (см. таблицу ниже):
   # Environment=STRELAY_PORT=25580
   # Environment=STRELAY_MAX_ROOMS=200

   [Install]
   WantedBy=multi-user.target
   ```

3. Включить и проверить:

   ```bash
   systemctl daemon-reload
   systemctl enable --now stlauncher-relay
   systemctl status stlauncher-relay
   journalctl -u stlauncher-relay -n 20
   ```

   В журнале должна быть строка `listening on port 25580`.

### Порт

Нужен один входящий **TCP 25580** (или тот, что задан в `--port`). Его надо открыть и в
файрволе самого сервера, и в панели хостера, если там есть свой:

```bash
ufw allow 25580/tcp
```

Лаунчер сейчас публичные адреса не предлагает (на сервере без проверки аккаунтов по такому
адресу зайдёт любой, кто знает ник из списка), поэтому на рабочем реле они выключены:
`--public-port-from 0`. Сама возможность в реле осталась. Для неё нужен диапазон **TCP 25600–25699**. Игрок включает этот способ,
и реле выдаёт его серверу один порт из диапазона: в лаунчере сразу появляется адрес вида
`ВАШ_СЕРВЕР:25612`, по которому друг заходит из обычного Minecraft, без лаунчера и без
аккаунтов. Порт выбирается по ключу комнаты, поэтому у одного и того же сервера адрес не
меняется от запуска к запуску.

```bash
ufw allow 25600:25699/tcp
```

Не открыт диапазон в файрволе — адрес будет показан, но зайти по нему не получится. Не
нужны публичные адреса вовсе — `--public-port-from 0`.

Проверка снаружи, с любого компьютера:

```bash
(printf 'PROBE 25565\n'; sleep 4) | nc ВАШ_СЕРВЕР 25580
```

Ответ `UNREACHABLE <ваш адрес>` (или `REACHABLE …`) значит, что реле работает и видно из
интернета. Ответ приходит не сразу: до трёх секунд реле пробует подключиться обратно.

### Обновление

Собрать заново, заменить файл, `systemctl restart stlauncher-relay`. Открытые комнаты
при этом рвутся, но лаунчеры хозяев переподключаются сами за несколько секунд с тем же
ключом, так что уже разосланные приглашения продолжают работать. Игроков, которые в этот
момент в игре, выкинет — обновлять лучше, когда никого нет (см. счётчики в журнале).

## Подключение к лаунчеру

Адрес реле лаунчер берёт из каталога. В корень `catalog.json` добавить:

```json
"friendsRelay": "ВАШ_СЕРВЕР:25580"
```

Можно домен, можно IP. Порт `25580` можно не писать. Как и остальной каталог, это
доезжает до всех игроков при следующем запуске лаунчера, без выпуска версии. Убрать
поле — способ «через реле» у всех выключится.

Адрес нужен только хозяину сервера: в приглашение (`STS1.…`) попадает тот адрес реле,
к которому хозяин подключён, поэтому гость подключится даже со старым каталогом.

Для проверки до публикации каталога есть переменная окружения — она важнее каталога:

```powershell
$env:STLAUNCHER_RELAY = '127.0.0.1:25580'
```

Реле на своём компьютере для такой проверки:

```powershell
.\artifacts\relay\win-x64\stlauncher-relay.exe --bind 127.0.0.1
```

С `--bind 127.0.0.1` оно слушает только этот компьютер и Windows не спрашивает про
файрвол.

## Настройки

Каждая задаётся в командной строке (`--max-rooms 50`) или переменной окружения
(`STRELAY_MAX_ROOMS=50`); командная строка важнее. Неверное значение — реле не
запустится и скажет, что не так. `stlauncher-relay --help` печатает этот же список.

| Опция | Переменная | По умолчанию | Что ограничивает |
| --- | --- | --- | --- |
| `--port` | `STRELAY_PORT` | 25580 | Порт TCP. |
| `--public-port-from` | `STRELAY_PUBLIC_PORT_FROM` | 25600 | Первый порт для публичных адресов. 0 — не выдавать. |
| `--public-port-count` | `STRELAY_PUBLIC_PORT_COUNT` | 100 | Сколько портов подряд можно выдать: столько серверов одновременно получат публичный адрес. |
| `--bind` | `STRELAY_BIND` | все адреса | Адрес, на котором слушать (IPv4 и IPv6, если не задан). |
| `--max-line` | `STRELAY_MAX_LINE` | 256 | Длина первой строки соединения, байт. Длиннее — соединение закрывается. |
| `--handshake-timeout` | `STRELAY_HANDSHAKE_TIMEOUT` | 10 | Секунд на первую строку. |
| `--max-rooms` | `STRELAY_MAX_ROOMS` | 200 | Комнат (серверов друзей) одновременно. |
| `--max-rooms-per-ip` | `STRELAY_MAX_ROOMS_PER_IP` | 4 | Комнат, которые может держать один адрес. Без этого несколько адресов могли бы занять все комнаты и не оставить их остальным. |
| `--max-guests` | `STRELAY_MAX_GUESTS` | 16 | Соединений гостей в одной комнате. |
| `--accept-timeout` | `STRELAY_ACCEPT_TIMEOUT` | 10 | Секунд, которые гость ждёт, пока лаунчер хозяина его подхватит. |
| `--idle-timeout` | `STRELAY_IDLE_TIMEOUT` | 120 | Секунд тишины, после которых туннель закрывается. |
| `--control-timeout` | `STRELAY_CONTROL_TIMEOUT` | 60 | Секунд без пинга от хозяина, после которых комната закрывается. Лаунчер пингует раз в 20 секунд. |
| `--rate-kbit` | `STRELAY_RATE_KBIT` | 1000 | Потолок скорости одного туннеля в каждую сторону, кбит/с. 0 — без потолка. |
| `--burst-seconds` | `STRELAY_BURST_SECONDS` | 4 | Сколько секунд потолка туннель может потратить разом после тишины: вход в мир грузит чанки рывком. |
| `--max-per-ip` | `STRELAY_MAX_PER_IP` | 48 | Открытых соединений с одного адреса. Хозяину нужно по одному на гостя плюс управляющее. |
| `--max-attempts` | `STRELAY_MAX_ATTEMPTS` | 120 | Новых соединений с одного адреса в минуту. |
| `--max-connections` | `STRELAY_MAX_CONNECTIONS` | 2000 | Соединений всего. |
| `--probe-timeout` | `STRELAY_PROBE_TIMEOUT` | 3 | Секунд на обратное подключение при `PROBE`. |
| `--stats-minutes` | `STRELAY_STATS_MINUTES` | 10 | Раз в сколько минут печатать счётчики. 0 — не печатать. |

Для IPv6 лимиты «с одного адреса» считаются по сети /64: у одного абонента их целая сеть.
Комнаты считаются шире, по /56: домашней линии обычно выдают именно столько, а это 256 сетей /64.

### Сколько это стоит серверу

Один игрок в Minecraft — это 20–100 кбит/с в спокойной игре и всплеск при входе в мир.
Потолок в 1 Мбит/с с запасом на 4 секунды этого не замечает, а превратить реле в
бесплатный туннель для чего-то тяжёлого не даёт. Худший случай по трафику — число
туннелей × 1 Мбит/с в каждую сторону. Памяти реле берёт по два буфера в 16 КБ на
туннель, остальное — сетевые буферы самой системы.

## Что реле знает и что пишет

- В журнал идут только запуск, остановка и счётчики: `rooms=3 connections=11 tunnels=4`.
  Ни адресов, ни ключей, ни содержимого.
- Адреса живут в памяти ровно столько, сколько нужно лимитам: запись стирается через
  минуту после последнего соединения с этого адреса. На диск реле не пишет ничего.
- Трафик Minecraft реле не разбирает и не хранит — только перекладывает.

## Протокол

Одна строка ASCII, затем сырые байты. Ключи — 128 бит, 32 шестнадцатеричных знака.

| Кто | Строка | Ответ |
| --- | --- | --- |
| Хозяин, управляющее соединение | `HOST <ключ хозяина>` | `OK`; дальше `PING` → `PONG`. Когда приходит гость, реле шлёт сюда `OPEN <id>`. |
| Гость | `JOIN <ключ комнаты>` | `OK`, когда хозяин подхватил; дальше байты. |
| Хозяин, соединение под гостя | `DATA <ключ хозяина> <id>` | `OK`; дальше байты. |
| Хозяин, управляющее соединение | `INVITE BEGIN`, строки `INVITE + <до 200 знаков>`, `INVITE END` | `INVITED`. Реле запоминает приглашение комнаты (до 32 000 знаков, только в памяти) под коротким кодом из 10 знаков, который следует из ключа комнаты. `INVITE CLEAR` забирает его. |
| Гость | `FETCH <короткий код>` | `OK <число строк>` и само приглашение строками; `ERR NOROOM`, если хозяин не в сети, `ERR NOINVITE`, если он ничего не оставил. |
| Кто угодно | `PROBE <порт>` | `REACHABLE <адрес>` или `UNREACHABLE <адрес>`: реле пробует подключиться обратно к тому, кто спросил, и только к нему. Порты ниже 1024 не пробует. |

Ошибки: `ERR NOROOM` (нет такой комнаты — хозяин не в сети), `ERR NOHOST`,
`ERR TIMEOUT` (хозяин не подхватил), `ERR FULL` (лимит комнат или гостей),
`ERR LIMIT` (лимит на адрес), `ERR BUSY` (лимит соединений), `ERR BADKEY`,
`ERR BADPORT`, `ERR BADCMD`.

**Ключ комнаты — не ключ хозяина.** Хозяин придумывает случайный ключ и держит его у
себя; ключ комнаты реле вычисляет из него (первая половина SHA-256). В приглашение
попадает только ключ комнаты. С ним можно зайти в комнату, но нельзя открыть её вместо
хозяина или перехватить чужих гостей — даже если приглашение утекло в общий чат.

`PROBE` лаунчер использует, чтобы честно проверить проброс порта: снаружи видно то, чего
изнутри не узнать.

### Голосовой чат (Simple Voice Chat)

Реле для этого не менялось: оно по-прежнему только перекладывает байты. Всё остальное —
договорённость двух лаунчеров (с версии 0.5.7) поверх обычного туннеля комнаты по
приглашению.

- Первый байт, который лаунчер гостя шлёт в туннель после `OK`, — метка канала: `G` —
  игра, `V` — голос. Лаунчер хозяина читает его первым: `G` ведёт на TCP-порт сервера
  Minecraft, `V` — на UDP-порт голосового сервера на той же машине, с отдельным
  UDP-сокетом на каждый туннель, чтобы голосовой сервер различал гостей по порту.
  Любой другой байт или его отсутствие закрывает туннель. Комната с публичным портом
  меток не использует: туда приходят обычные клиенты Minecraft.
- В голосовом туннеле идут датаграммы: 2 байта длины (big-endian), затем сама датаграмма,
  от 1 до 1500 байт. Кадр другой длины закрывает этот туннель, и только его.
- Гость слушает UDP `127.0.0.1:<порт голоса>`: мод шлёт голос на адрес, по которому игра
  зашла на сервер (при способе «Только для своих» это сама машина гостя), и на порт,
  который назвал сервер. Порт приходит в приглашении (`voicePort`). На каждого
  отправителя — свой туннель; молчащий туннель гость закрывает через 100 секунд, раньше
  самого реле.
- Голосовой туннель — такой же гость комнаты, как и игровой: каждый игрок с голосовым
  чатом занимает два места из `--max-guests` (по умолчанию 16), и голос входит в тот же
  потолок скорости на туннель. Голос — это десятки кбит/с, так что потолок его не замечает.
